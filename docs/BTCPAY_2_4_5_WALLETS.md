# Blink and NWC on BTCPay Server 2.4.5

Build against the pinned v2.4.5 host (`5d0745cae6be5d8210459e38813f317673aa97b8`) with .NET 10. Blink 1.1.3 and Nostr/NIP05 1.1.22 require host 2.4.5. The NWC test project is included by the existing CI test glob.

Blink address mode continues accepting `type=blink;ln-address=name@blink.sv;`. New merchant-key setup may use its real LNURL origin: `type=blink;ln-address=name@blink.sv;server=https://blink.sv;`. The optional server must match the address origin. No dummy endpoint or merchant server permission is needed. Custodial and address clients now use guarded HTTP transport with HTTPS by default, DNS-pinned connection checks, no redirects, and a 30-second timeout. Internal HTTP endpoints require an exact origin in `BTCPAY_PLUGIN_HTTP_ALLOWED_HTTP_ORIGINS` and a matching narrow `BTCPAY_SSRFEXCEPTIONS` entry.

NWC has no legitimate HTTP server parameter. Instead, `PUT /api/v1/stores/{storeId}/nwc/connection` accepts only `{ "uri": "nostr+walletconnect://..." }` under Greenfield `CanModifyStoreSettings` authorization. It checks the authorized store context, validates URI/keys and one to eight relays, refuses replacing wallets while invoices are still monitored (including archived invoices and Processing), validates the wallet, and writes only an NWC configuration. It returns no URI or secrets and leaves `AllowUnsafeConnection=false`. Existing URI syntax and NIP04/NIP44 behavior are preserved.

Each NWC operation uses a guarded WebSocket client through BTCPay's SSRF transport. Connections resolve and connect to checked IP addresses, reject redirects, honor cancellation, and have a 10-second handshake deadline. Relay clients and their transports are disposed together. WSS is required by default; operator-authorized internal WS endpoints need an exact origin in `BTCPAY_NWC_ALLOWED_WS_ORIGINS` and a narrow core SSRF exception. These exceptions do not authorize other ports or hosts. NWC relay logs omit query tokens. The transport replaces the upstream client pool because its WebSocket construction cannot accept the host's guarded HTTP invoker; this trades connection reuse for enforceable network safety. Validate polling, notification reconnects, and performance with staging wallets.

The endpoint checks pending invoices, but unrelated external configuration writers must be quiesced while switching wallets; Satflux additionally serializes wallet changes with its own invoice creation and journals uncertain outcomes. No BTCPay core changes, privileged provisioning key, migration changes, or production installation are included.

Existing Blink tests, NWC URI/exception tests, and real loopback socket-denial regressions cover source behavior. An isolated 2.4.5 host confirms plugin loading, store authorization, foreign-store denial, pending-invoice refusal, and private relay rejection. Public-wallet onboarding, invoice payment, settlement, and NWC reconnect recovery still require funded staging wallets. Deploy the host and these packages together before enabling wallet changes. Roll back the matched host/plugin set under maintenance, preserving stored wallet URIs and invoices.
